# Use OSS as the CDN origin for member assets

Status: accepted

The member H5 build's hashed files under `dist/assets/` will be published to the dedicated private Alibaba Cloud OSS Bucket `feilesaigecn` in `cn-shenzhen` and served to users through `cdn.feilesaige.cn` using same-account CDN private-Bucket origin access; the light application server remains responsible for the entry page, Laravel API, sessions, and administration routes. We chose this boundary over using the light server as the CDN origin so static cache misses do not consume application-server CPU and bandwidth, while dynamic registration traffic remains observable and independently testable at the application origin.

Consequences: the deployment configuration must use the new CDN hostname and OSS bucket, only `frontend/member-h5/dist/assets/` is published under the OSS `assets/` prefix, the CDN acceleration scope is China Mainland Only because the domain has a valid ICP filing, the upload credential needs only the minimum write/list permissions, CDN must be authorized for private-Bucket reads, `/assets/*` uses long-lived immutable caching while old hash files are retained, HTTPS/CNAME settings must be configured separately, and the 200-user acceptance test must measure both CDN asset delivery and origin API/registration behavior. The current origin constraint is a 2-vCPU, 2-GiB light server running PHP-FPM, MySQL, Redis, queue, and scheduler together; the existing 512-MiB PHP memory limit makes memory pressure an explicit test gate. Because no separate staging environment exists, validation will use isolated synthetic production data and a controlled ramp-up rather than real member accounts or live race submissions; test records remain until the owner approves the results, and cleanup is manual.

Acceptance gate: 200 users must enter, log in, view a race, and open the registration page within 60 seconds; 20–30 synthetic users must submit registrations concurrently. API errors must remain below 1%, read-flow P95 must stay below 2 seconds, submission P95 below 3 seconds, no 502/504/timeout/OOM/swap may occur, sustained CPU and memory should remain below approximately 85%, CDN assets must return 2xx and become edge-served after warm-up, and submissions must be complete and non-duplicated.
